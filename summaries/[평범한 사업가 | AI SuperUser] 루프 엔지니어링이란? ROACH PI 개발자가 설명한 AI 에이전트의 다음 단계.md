## **AI가 삶을 변화시키는 특별한 방법을 탐구하는 팟캐스트 소개**

- '평범한 사람들' 팟캐스트임.

- 진행자 유튜버 '평범한 사업가'임.

- 오늘 게스트는 AI 에이전트를 도구가 아닌 하드웨어처럼 재설계하며 사용하는 정승현 개발자임.

- 정승현 개발자는 릿에서 개발자로 일하며, 프롬프트 세이버 roach-pi, roach-code 등 실용적인 오픈 소스 도구를 직접 만들어 공유해옴.

## **정승현 개발자 자기소개**

- 정승현이라 함.

- 릿에서 소프트웨어 엔지니어로 일하고 있음.

- 이전에는 배민에서 엔지니어로 일했음.

- 최근에는 하네스 엔지니어링이나 클로드 코드 코덱스 등에 관심이 많아 여러 툴을 만들고 있음.

- 만든 툴들을 스레드, 링크드인, 유튜브에 올리며 활발히 활동 중임.

## **roach-pi 소개 및 기능**

- 정승현 개발자는 다른 유명 개발자들로부터 가장 핫한 개발자로 추천받아 섭외됨.

- roach-pi는 오픈 소스로 나와 있는 'Pi'라는 가벼운 하네스 엔진 위에 개발자가 주로 쓰는 스킬과 에이전트 코딩 방법론을 씌운 것임.

- Claripi를 통해 유저가 프롬프트를 입력하면, 모호도를 계속 낮출 때까지 인터뷰를 진행함.

- OMX나 OMC 사용자들은 익숙할 방식임.

- 현재는 '골(Goal)'을 돌리는 골 지향적인 하네스임.

## **roach-pi와 기존 하네스(OMX, OMC, 우로보로스)의 차별점**

- 워크플로우가 기존 OMX, OMC, 이재균 개발자의 우로보로스와 유사하게 작업 전 명확화 과정을 거침.

- 엄청난 차별화는 없다고 생각함.

- OMX나 우로보로스는 모호도를 수학적으로 계산하지만, roach-pi는 Claripi에서 명확하게 만드는 데 집중함.

- 개발자는 Claripi 에이전트가 이해했다고 생각할 때까지 명확화 과정을 끝내지 않는 성격이라, 점수 같은 것은 필요 없어 넣지 않았다고 함.

## **비개발자를 위한 roach-pi의 효용성**

- 레이지 코덱스처럼 '딸깍' 하는 방식은 아니지만, AI 에이전트가 "어떤 점이 문제야?", "네가 하고 싶은 게 뭐야?"라고 되묻는 과정이 있음.

- 이러한 질문 과정을 통해 비개발자나 비전공자도 본인이 하고자 하는 것을 더 명확하게 만들 수 있음.

- 장점: 원하는 것을 명확히 하는 데 도움 줌.

- 단점: AI가 어려운 것을 계속 물어보기 때문에 특정 구간에서는 허들이 될 수도 있음.

## **인간의 병목 현상과 roach-pi의 극복 방안**

- AI 작업 시 인간이 생각지 못한 질문에 답해야 하는데, 인간의 답변 수준이 낮아지는 현상이 발생함.

- 에이전트 '스티어링' 능력이 사람마다 달라, 결국 인간이 병목이라는 논의가 계속됨.

- roach-pi는 토큰을 적게 쓰는 방향을 선호하여 만들어짐.

- 안드레 카파시의 "이해는 아웃소싱할 수 없는 물질"이라는 말에 공감함.

- 메타에서 ML 추천 알고리즘을 클로드 코드로 만드는 사람은 만들 수 있지만, 백날 토큰 맥싱해도 만들지 못할 것이라 생각함.

- AI 에이전트가 이 갭을 메워줄 수는 있지만, 아직 하방(인간의 이해 수준)이 충분히 올라오지 못했다고 봄.

- roach-pi는 "너 이해 안 하려 하지 마", "네가 이해하려고 노력해"라는 메시지를 담고 있음.

## **AI 모델 발전 방향 및 인간 개입의 미래**

- 최근 파(Pavel), 클로드 코드 워크플로우는 인간 개입을 최소화하고 에이전트가 스스로 결정하는 방향으로 나아감.

- 장단점이 존재함. 모델 성능이 GPT 5.5, Opus 4.8까지 발전.

- RALF 루프의 한계는 에이전트의 잘못된 가설이 계속 쓰레기만 쌓는 결과를 낳는 것임.

- 오늘 공개된 파벨 5는 많은 토큰을 소모하지만, 기존 에이전트보다 기대 이상의 결과물을 내놓기 시작함.

- 이 시점에서는 인간 개입이 필요 없다는 생각도 들 수 있지만, 파벨 5는 테스트 중 중단되는 경우가 많아 아직 상용화에는 시간이 필요하다고 봄.

- 결국 그전까지는 하네스를 얼마나 잘 깎느냐가 중요할 것으로 예상함.

- 개발자는 사람이 루프 안에 있어야 한다고 생각하지만, 그 역할은 앞단(의도 제공, 에이전트 지원)과 뒷단(검증, 책임)이라고 봄.

- 인간도 LLM 하네스의 한 요소라고 간주함.

- 파벨 5는 주어진 일을 구조 분해하는 능력이 엄청나게 뛰어남. 루프 엔지니어링과 관련이 깊음.

- 작업을 수행하면서 구조 분해를 하고, 작은 컨텍스트로 쪼개 서브 에이전트에게 할당하는 것이 중요함. 파벨 5가 이를 잘함.

- 클로드 코드 게시물에서 서브 에이전트의 중첩 깊이를 늘린다고 한 것은, 파벨 5를 써보고 구조 분해 능력을 인지했기 때문이라고 생각함.

- 하네스가 하던 역할을 이제 모델이 하는 느낌을 강하게 받고 있음.

## **다이나믹 워크플로우, CodeX 앱, '골' 기능 활용 팁**

- 클로드의 다이나믹 워크플로우는 누구나 쉽게 하네스 엔지니어링을 할 수 있도록 나온 기능으로 보임.

- 파벨 5로 다이나믹 워크플로우를 돌리면 토큰 소모가 너무 많아 (오푸스 4.8로도 많았음) 몇십 분 만에 중단되는 경우가 많음.

- 기존에 하네스로 깎던 작업들을 모델과 빌트인 워크플로우로 커버하려는 움직임은 사용자 및 개발자 니즈를 빠르게 반영한 것 같음.

- 코덱스 앱은 매우 편하고, 과거 개발자 중심에서 비개발자도 쓰기 좋아짐.

- 클로드는 다이나믹 워크플로우를 보며 앞서 나간다고 생각함.

- 코덱스 '골' 잘 사용하는 팁:

- 골을 돌리기 전 AI 에이전트와 "무엇을 하고 싶은지" 명확하게 다듬는 턴을 많이 가져감.

- 예시: 에이전트에게 코드베이스 확인 요청, 구현 방법 문의 등을 통해 충분히 명확해지면 골로 "구현해 줘"라고 지시함.

- '적대적 리뷰어' 꿀팁: 깐깐하고 비평적인 리뷰어에게 검토받기 전까지 골을 끝내지 말라고 설정하면 작업 완수율이 30% 정도 올라감.

## **CodeX 앱의 스레드 관리와 컨텍스트 엔지니어링**

- 코덱스 개발자들이 스레드 관리의 중요성을 강조하고 있음 (자동 핀 설정, 오래된 스레드 아카이브).

- CLI 사용자들은 대부분 세션을 계속 클리어했지만, 코덱스 앱에서는 유사한 작업들을 하나의 스레드 안에서 계속 이어서 진행하라고 권고함.

- 유사한 작업을 하나의 스레드에서 하는 것은 대화를 압축할 때 LLM에게 유사한 정보를 계속 밀어주는 것이 중요하기 때문임.

- 오픈AI는 컨텍스트 압축 시에도 의도를 잘 기억하는 능력이 뛰어남.

- 따라서 유사한 스레드를 많이 넣어 관리하라는 오픈AI 팀의 강조는 중요한 개념임.

## **메모리 시스템과 roach-pi의 메모리 철학**

- 메모리 시스템은 한동안 핫한 주제였음 (오픈 클로우 메모리 시스템 시도).

- roach-pi는 키워드 기반으로 검색하는 방식으로 굳어짐 (예: '강남 맛집' 검색 시 '강남'으로 검색).

- 에이전트에게 도구를 주면 유사도 검색보다 더 잘 찾고, 검색어도 잘 넣음.

- roach-pi는 코딩 툴이므로 장애, 디버그, 픽스 관련 키워드가 대화에 나오면 LLM이 정리하여 메모리에 저장함.

- 이후 찾아볼 수 있도록 함.

- 메모리 시스템에서 중요한 것은 오래된 메모리를 잘 지워주는 것임 (옛날 코드가 빠르게 deprecated 되므로).

- roach-pi는 200개 정도만 저장하고 나머지는 지워지는 구조로 만듦.

- 개발자는 롱텀 메모리가 그렇게 좋다고 보지 않음. 사람도 살면서 중요한 기억만 남기듯이, 사람 정도의 일을 하는 데는 그렇게 장기 기억이 필요 없다고 생각함.

- 현재는 토큰 소모가 너무 많아 롱텀 메모리 검색이 비효율적임 (예전 오픈 클로우 사용 경험).

- 미래에는 LLM이 컴퓨터라면 저장소(하드웨어)에서 찾아오는 알고리즘이 개발될 것이고, 그때는 사용할 수 있을 것이라 봄. 현재 엔터프라이즈에서는 무리가 있다고 생각함.

## **루프 엔지니어링의 재부상과 발전**

- 피터 스테인버그가 "더 이상 프롬프트를 얘기하지 말고 루프를 설계하라"는 트윗이 바이럴됨.

- 루프 엔지니어링은 새로운 개념은 아니지만, 골과 클로드의 다이나믹 워크플로우가 이 범주에 속하며 다시 각광받고 있음.

- 루프는 반복을 의미함.

- 기존에는 작업이 끝나고 결과가 완수되지 않으면 사람이 루프를 재개해야 했음.

- 현재의 루프 엔지니어링은 골처럼 '의도에 도달할 때까지 루프가 끝나지 않게' 만드는 것임.

- 목적 달성까지 루프를 어떻게 유지할지, 평가 지표를 얼마나 잘 짤지가 공학적인 엔지니어링 분야임.

- 개발자는 현업에서 골을 사용하며 루프 엔지니어링을 하고, 클로드 코드의 루프나 코덱스의 오토메이션(리뷰 처리, 에러 발생 시 PR 생성)도 루프로 간주하여 활용함.

- 비개발자에게는 생소하고 막연할 수 있음.

- 랄프 루프(6개월~1년 전 유행)와 현재 루프 엔지니어링의 차이:

- 과거 랄프 루프는 스펙이 제대로 잡히면 '와일 루프'처럼 단순히 반복시키는 방식이었음. 루프 밖에서 고민을 많이 하고, 루프 안에서는 사람의 개입이 불가능했음.

- 현재 루프 엔지니어링은 루프 안에서의 고민을 시작함. 바깥에서는 좀 더 추상적으로 맥락을 정의하고, 그 안에서 에이전트가 다른 에이전트를 조절(스티어링)함.

- '에이전트가 에이전트에게 프롬프트를 넣게 하라'는 클로드 코드 개발자의 말처럼, 루프 안에서 에이전트끼리 스티어링하는 방식임. 골도 이런 식으로 사용함.

## **AI 모델 발전의 급진적 변화와 향후 방향성**

- AI 에이전트의 발전 속도가 너무 빨라 초보자들은 혼란스러워하며, 좋은 기능은 비용 부담이 큼.

- 코덱스 앱 정도는 초보자에게 유용하다고 봄. 루프 엔지니어링 개념이 다음 코덱스 앱에 강력한 기능으로 도입될 것이라 예상함.

- 파벨 5의 발표는 기존의 GPT 5.5 vs Opus 4.8 논의를 무색하게 할 정도로 찬사가 쏟아짐.

- 개발자는 파벨 5를 사용하며 매우 놀랐음. 갤러그 게임 벤치마크 (두 줄 프롬프트로 게임 제작)에서 파벨 5는 에셋도 만들지 않았는데 옛날 게임기 수준으로 만들어버림.

- 클로드 3.5에서 4.5로 넘어갈 때의 변화보다 훨씬 아득한 지평선을 넘었다고 느낌. 다른 모델들과 다른 레벨에 있다고 봄.

- 앞으로 하네스는 높은 확률로 모델이 흡수할 것이라 예측함.

- 클로드는 파벨 5를 빠르게 토큰 플랜이나 API에 넣어, 루프 안에서 일을 할당할 때 소넷, 하이쿠, 오푸스 같은 모델에 효율적으로 분배하는 것이 중요하다고 봄. 이것이 버짓 컨트롤이며 경제적인 루프 운영 메커니즘을 완성할 것임.

- 에이전트가 일을 잘하기 위한 하네스는 이제 손 뗄 때가 된 것 같다고 생각함.

- 인간은 에이전트에게 도메인 지식을 최대한 열어주고, 앞으로는 의도와 평가 지표를 세우는 역할에 집중해야 할 것임.

## **토큰 신분제와 중국/오픈 소스 모델의 위상**

- AI 모델 발전이 가속화되면서 '토큰 신분제'가 부활할 것 같다는 우려가 있음.

- 모델을 쓸 수 있는 여력이 되는 사람들은 엄청난 일을 해내지만, 그렇지 못한 사람들은 격차가 벌어질 수 있음.

- 토큰 값은 절대 싸지지 않을 것이라 예측함 (석유나 비싼 전기처럼 공급될 확률 높음).

- 사람들이 한때 "오푸스 4.6급 중국 모델 나오면 쓴다"고 했지만, 지금 아무도 쓰지 않음. 이는 말도 안 되는 이야기라고 생각함.

- 중국 모델 (Qwen 3.7 Max, MiMo V2.5 Pro)은 오푸스 4.6 정도의 성능을 보인다고 평가함. 하네스에서 돌렸을 때 코드 수정이 적었음.

- 현재 중국 LLM들은 규모의 경제를 추구하며 추론 효율을 높여 저렴하게 서비스하려는 경향이 있음 (딥시크).

- 엔지니어링 실력이 좋다면 굳이 비싼 토큰 값을 낼 필요 없이 샤오미 미모나 딥시크, Qwen 맥스 정도면 괜찮다고 봄.

- 중국 프론티어 모델은 개발에는 큰 무리가 없으나, 내부 시스템에서는 무리가 있음.

- 가장 큰 문제는 중국어를 많이 사용하며, 엔지니어링이 아닌 업무에서는 성능이 떨어져 토큰을 더 많이 소모할 수 있음.

- 기업 내부 에이전트 구축 시에는 아직 미국 SOTA 모델을 쓰는 것이 경제적임.

- 지능이 오를수록 중국어 출력은 줄어들며, 딥시크 V4 프로는 거의 중국어를 뱉지 않는다고 함.

## **프롬프트 캐싱 효율화와 Liziness 활용**

- 딥시크 V4 모델은 캐싱 능력이 발전하여 토큰 효율이 높고 프롬프트 캐시 가격이 개선됨.

- 캐시의 중요성: 프롬프트 일부만 바뀌어도 캐시 적중률이 떨어지며 응답 속도 저하, 비용 증가 (1~2달러 갑자기 지불)가 발생함.

- 과거 클로드 코드/코덱스의 문제는 세션 중 퍼미션을 바꾸면 캐시가 깨지는 것이었음.

- 리즈니스(Liziness)라는 레포지토리를 사용하면 이런 캐시 깨짐을 방지하거나 경고함.

- 리즈니스를 사용한 딥시크은 캐시가 적중하면 0.063달러 정도만 내어, 1시간 사용해도 1달러도 안 나오는 경우가 많음.

- 리즈니스 활용 팁: 딥시크나 샤오미 미모와 함께 사용해야 함. 권한은 처음에 설정한 것을 유지하고 도중에 바꾸지 않아야 함. 클로드 코드나 코덱스에서 만든 스케일을 가져올 수 있어 사용에 큰 어려움은 없음.

- roach-pi에 리즈니스 기능을 도입할 계획은 파이(Pi) 내부를 건드리게 되어 어려울 것으로 예상함.

- 사용자들이 신경 쓰지 않아도 가격 및 성능 효율적으로 모델과 서비스가 고도화되고 있음. 중국 모델들은 이 부분에서 미국의 프론티어 모델보다 우수하다고 느낌.

## **콘텐츠 제작 활동과 바이오 토큰 개념**

- 개발자는 과거부터 기술 블로그 운영 등 공유 활동을 좋아했음 (5~6년간 블로그 운영).

- AI 시대가 오면서 본업의 일이 줄어들어 "나는 무엇을 해야 하나"라는 고민 끝에 SNS, 유튜브 활동을 시작함.

- AI에 노동을 맡기고 자신은 다른 표면으로 나가고자 스레드를 시작함.

- 헤르메스 에이전트를 소개하며 팔로워가 빠르게 늘었고, 일상 및 스레드 활동 자동화로 유튜브 활동 여력도 생김.

- 하이퍼 프레임, 리모션, 비디오 유즈 등 AI 영상 편집 툴을 활용하여 애니메이션 영상 (쓰리블루원브라운 같은 다큐멘터리) 제작을 토큰 맥싱하며 시도하고 있음.

- 바이오 토큰: AI 시대가 오면서 사람이 더 많은 일을 하게 되었고, 엉덩이 무겁게 앉아있어야 하므로 사람에게도 '토큰'이 있음.

- 5시간 동안 토큰을 다 쓰면 채워야 하며, 많은 토큰을 가지려면 운동과 식단 관리가 필요함.

- 개발자는 점심시간에 1시간씩 운동하며 에이전트를 더 많이 부리기 위해 자신의 토큰을 늘리고 있음.

- 결국 AI가 일하겠지만, 일을 시키는 사람이 체력적, 정신적으로 건강해야 제대로 된 작업을 시킬 수 있다고 생각함.

## **향후 로드맵 (roach-pi 및 개인 개발자로서)**

- 홍보: 유튜브 'roach의 개발 일기' 및 스레드 'roach' 검색 시 많은 글을 볼 수 있음.

- roach-pi 로드맵:

- 하네스는 모델에 흡수될 것이라 보므로, roach-pi는 앞으로 더욱 '손을 뗄 것임'.

- 에이전트가 루프 안에서 자바스크립트 코드를 생성하여 에이전트를 조율하는 다이나믹 워크플로우 개념을 roach-pi에 녹이려 함.

- 클로드를 roach-pi에 직접 붙이기 어려워 코덱스에서 프론티어 모델이 나올 때 상황을 보고 진행할 것임.

- Claripi가 빠지고 '울트라 워크' 같은 기능만 남을 수도 있음.

- 최대한 사람은 앞단에서 조율만 하고, 하네스는 내부에서 모델을 계속 조율하여 루프를 잘 돌릴 수 있게 할 것임.

- 내부적으로 서브 에이전트에게 경제 효율적으로 서빙할 수 있을지를 측정하고 roach-pi에 녹일 것임.

- 개인 개발자 로드맵:

- 코딩 노동은 점점 없어지고 있다고 생각함. 엔지니어가 어려워했던 복잡한 시스템 설계 (예: 송금 보장)가 본질적으로 중요해질 것임.

- 컴퓨터 공학에서 컴퓨터 과학 쪽으로 옮겨가, 컴퓨터 동작 원리, 안정적인 시스템 설계 등을 에이전트와 주고받으며 더 좋은 시스템을 만들려 함.

- 노동은 에이전트가 하게 되고, 엔지니어는 설계와 본질적인 공부에 집중하게 될 것임.
